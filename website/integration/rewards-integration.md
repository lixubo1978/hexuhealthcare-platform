## 接口配置

修改 `public/rewards-config.js`：mode 改为 `live`；catalogUrl、accountUrl、checkoutIntentUrl 填工程师现有接口地址；checkoutOrigin 填现有下单页面的可信源（协议、域名及端口）。接口路径不在本项目中假设，当前没有与真实会员/订单接口连通。

沿用现有会员登录会话。建议通过同源 API 网关接入；跨域时须正确配置会话、CORS、CSRF 防护，禁止使用浏览器自报会员身份。积分账户返回 `{ "availablePoints": 100 }`。

目录返回 `{ "categories": [...], "items": [...] }`，分类结构见 rewards-preview.json。真实商品字段示例：

```json
{"id":"existing_product_id","categoryId":"household_wash","title":"商品名称","kind":"physical","imageUrl":"/商品图片地址","pointsPrice":80,"stock":12,"eligible":true,"fulfillmentModes":["delivery","pickup"],"isPreview":false}
```

以上数字仅为接口示例。kind 为 physical 或 service；stock 是后台计算的可兑换数量（服务应映射可预约资源数量）；pointsPrice 为非负数字。商品 id 必须复用现有商品/服务标识。规格、SKU、serviceId、门店与技师关联保留在原订单系统中。目录展示积分价格，不对外提供现金购买入口。真实图片建议统一比例，名称两行以内，卡片显示所需积分、库存状态和领取方式。

兑换按钮 POST checkoutIntentUrl：

```json
{"productId":"existing_product_id","orderType":"REDEMPTION","kind":"physical","source":"points_catalog","idempotencyKey":"uuid"}
```

服务器验证会话、商品类型和可兑换资格，返回 `{ "checkoutUrl": "https://现有下单域名/订单确认入口" }`。前端只跳转到 checkoutOrigin 配置的可信源。此接口只创建短期确认上下文，不扣积分、不完成订单；同一确认上下文重复提交使用同一幂等键。页面刷新或再次点击产生新上下文也不得直接扣款。

## 复用现有下单流程

实物：选礼品 → 选规格/数量 → 选邮寄或服务站自取 → 展示积分、运费与收货信息 → 确认兑换。

服务：选服务 → 选门店 → 选技师/服务人员及时间 → 确认积分订单。复用已开发的选择组件、预约能力与分成规则适配，不新建另一套服务订单。

统一订单类型 REDEMPTION、支付方式 POINTS，在现有订单列表显示。页面当前只传商品标识，不传价格或积分余额；后端最终报价并校验可用积分、SKU库存/预约资源、配送区域。未设置服务站时提供邮寄；自取只展示已开放且有库存的领取点。婴儿车和床等大件需提前显示运费、安装与配送限制。积分抵扣服务以及可能的现金补差须由现有结算规则明确。

## 积分与交易一致性

沿用现有积分账本，积分无有效期。本人有效现金消费与符合平台规则的转介绍消费，各按符合规则现金消费金额的5%计积分（每100元5积分）；小数积分、退款与关系归属按新版接入说明执行。1积分按1元用于指定兑换/抵扣，不支持提现。积分兑换部分不得再次生成消费积分，防止循环发放；分成与积分成本由现有规则核算，避免重复记账。

提交最终订单时，在事务内校验/冻结积分与库存（或预约资源），使用幂等键防重复扣减；成功履约核销，取消/超时/退款按规则释放或退回，部分退款保持账目对应。分布式系统需补偿和对账。所有变动有订单号、会员、原因与流水记录，管理员不可仅修改浏览器余额。

## 上线验收

检查八类过滤、搜索、缺货/空列表及手机布局；实物规格与配送费用、服务选门店/技师/预约衔接；未登录、积分不足、并发抢最后一件、重复提交、取消与退款、接口失败重试；确认浏览器篡改价格不能影响后端报价，现有普通服务下单和合作留言功能正常。
